\chapter*{ABSTRACT}
\addcontentsline{toc}{chapter}{ABSTRACT}
\thispagestyle{plain}

UniPlanner is a high-performance, web-based Learning Management System (LMS)
designed to streamline academic administration and foster collaborative learning
across three distinct user roles: students, teachers, and administrators.
The platform integrates structured course management, assignment tracking,
teacher-assisted feedback, real-time notifications, and a rich analytics dashboard
into a single unified interface. By providing role-specific portals, UniPlanner
addresses the fragmentation commonly found in traditional academic tools and
single-purpose applications.

Students benefit from an interactive dashboard displaying pending assignments,
enrolled courses, grade history, and upcoming deadlines. Teachers are empowered
with class management tools, a SpeedGrader for rapid assignment evaluation, and
manual submission feedback for students. Administrators gain full visibility over
platform health, user distribution, and system-wide analytics. The system is built
on a Node.js and Express.js backend with Firebase-backed data persistence,
JWT-based authentication (JSON Web Token), and a responsive Tailwind CSS frontend
accessible across desktop and mobile devices.

\vspace{0.5cm}
\noindent\textbf{Keywords:} Learning Management System, Educational Platform,
Assignment Tracking, Role-Based Access Control, JWT Authentication,
Real-Time Notifications, Analytics Dashboard.

\chapter{Introduction}

\section{Introduction}

In the current era of digital transformation, educational institutions face
significant challenges in managing the complex interactions between students,
educators, and administrators. Traditional academic management tools are often
fragmented, requiring separate platforms for course management, assignment
tracking, grading, and communication. This fragmentation leads to inefficiency,
information silos, and a diminished learning experience for students and
educators alike.

UniPlanner -- A Learning Management System is an all-in-one web-based educational
platform designed to unify these activities under a single, responsive interface.
It caters to three primary user roles: students who need to track their coursework
and grades; teachers who manage classes, assignments, and student evaluations; and
administrators who oversee platform health, user accounts, and system analytics.
The platform leverages modern web technologies including Node.js,Express.js, and
Firebase to deliver a real-time, role-aware experience that scales with
institutional needs.

A key differentiator of UniPlanner is its built-in Teacher module, which provides
students with submission feedback and quiz generation from learning materials, and
offers teachers discussion summarisation. This reduces the cognitive burden on
educators while giving students timely, actionable guidance before final submission.

\section{Problem Statement}

Educational institutions worldwide struggle with tool fragmentation. Students must
navigate multiple disconnected platforms to access their course materials, submit
assignments, check grades, and communicate with instructors. Teachers spend
disproportionate time on administrative tasks such as tracking submissions,
managing class rosters, and providing individual feedback. Administrators lack
centralised visibility into platform usage, engagement, and student performance.

Furthermore, the absence of timely feedback mechanisms means students often
receive grades only after submission, leaving no opportunity for improvement.
Existing commercial LMS platforms are expensive, heavily featured beyond
institutional needs, and often inaccessible on low-bandwidth or mobile connections.
There is a clear need for an affordable, role-aware, and enhanced educational
management system that consolidates all critical academic functions into a single,
intuitive platform.

\section{Project Objectives}

\begin{itemize}[leftmargin=2.5em]
  \item To develop a unified, role-based LMS supporting students, teachers, and
        administrators from a single web application.
  \item To implement a class and assignment management system with real-time state
        synchronisation.
  \item To provide a comprehensive analytics and reporting dashboard for each user
        role.
  \item To implement secure JWT-based authentication with role-based access
        control (RBAC).
  \item To enable file-based resource management with cloud storage integration
        via Cloudinary.
  \item To deliver a responsive, accessible UI using Tailwind CSS that works
        across devices.
\end{itemize}

\section{Significance of Project}

UniPlanner addresses a critical gap in academic management by providing a single
platform that serves all stakeholders in the educational ecosystem. For students,
it reduces the cognitive overhead of managing multiple tools, enabling them to
focus on learning rather than logistics. The gamification elements---i.e.,
experience points (XP), badges, and streaks---motivate consistent engagement and
reward academic effort.

For teachers, UniPlanner's Speed Grader and manual submission feedback
significantly reduce the time spent on assessment, allowing educators to provide
more nuanced feedback to more students. The quick-create assignment tool further
reduces administrative overhead. Administrators benefit from real-time platform
analytics that enable data-driven decisions about class management, resource
allocation, and platform health.

Beyond individual roles, UniPlanner promotes a culture of transparency and
accountability within educational institutions. Its open architecture, built on
standard web technologies, allows future extensibility and integration with
external systems such as student information systems (SIS) and video conferencing
platforms.

\section{Limitations of the Project}

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{Offline Functionality:}
    The application requires an active internet connection. Students in
    low-connectivity environments may face difficulties accessing the platform,
    limiting its reach in rural or underdeveloped regions.

  \item \textbf{No Video Conferencing Integration:}
    UniPlanner does not currently integrate with video conferencing platforms
    such as Zoom or Google Meet. Live virtual class sessions must be managed
    through external tools.

  \item \textbf{Mobile Application:}
    The platform is currently accessible via a responsive web interface only.
    A dedicated native mobile application for iOS and Android has not been
    developed.

  \item \textbf{Single Language Support:}
    The system currently supports only the English language, limiting usability
    for non-English speaking institutions. Internationalisation (i18n) support
    can be added in future iterations.
\end{itemize}

\section{Development Methodology}

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{Agile Scrum Methodology:}
    UniPlanner was developed following the Agile Scrum methodology, which
    emphasises iterative development, continuous collaboration, and adaptability
    to changing requirements. Development was organised into time-boxed sprints,
    with each sprint delivering a functional increment of the platform. Sprint
    planning sessions defined the features to be built, daily stand-ups ensured
    team alignment, and sprint reviews validated delivered functionality against
    project requirements.
\end{itemize}

This methodology was particularly well-suited to the UniPlanner project because it
allowed the team to rapidly prototype individual modules (authentication, class
management, assignments, etc.) and integrate them incrementally, reducing
integration risk and enabling early usability feedback.

\chapter{Background Study and Literature Review}
%============================================================

\section{Background of the Study}

The rapid growth of digital education has driven widespread adoption of Learning
Management Systems across universities, colleges, and K--12 institutions worldwide.
Platforms such as Moodle, Canvas, Blackboard, and Google Classroom have
demonstrated the value of centralising academic activities in a single digital
environment. However, these platforms are often too complex, too expensive, or too
rigid for smaller institutions or rapidly evolving curriculum structures.

In Nepal, where Phoenix College of Management operates, internet infrastructure
and device accessibility continue to improve, creating new opportunities for
digital learning tools. Yet most institutions still rely on fragmented
communication channels---WhatsApp groups, email threads, and shared drives---for
assignment distribution, submission, and feedback. This fragmentation contributes
to delayed feedback cycles, lost submissions, and poor visibility into student
progress.

UniPlanner was conceived to address this institutional need by providing a
lightweight, open-architecture LMS that can be deployed with minimal
infrastructure, runs in any modern browser, and offers role-specific experiences
tailored to the actual workflows of students, teachers, and administrators in a
BIT programme.

\section{Literature Review}

Learning Management Systems have been extensively studied in the educational
technology literature. Siemens and Long~\cite{siemens2011} argued that the next
generation of LMS platforms must move beyond content delivery toward adaptive
learning and analytics-driven insights. This vision directly informs UniPlanner's
analytics dashboard and role-specific performance metrics, which aim to provide
stakeholders with actionable data rather than raw activity logs.

Brown and Adler~\cite{brown2008} emphasised the importance of participatory
learning and peer collaboration in digital education environments. UniPlanner's
discussion threads, messaging system, and collaborative resource-sharing features
are designed to support these participatory learning models, enabling students to
engage with course content beyond passive consumption.

Shute~\cite{shute2008} demonstrated that formative feedback---provided before and
during the learning process rather than only after assessment---significantly
improves student outcomes. UniPlanner's submission feedback module supports this
principle by enabling teachers to provide structured feedback on student drafts
prior to the final submission deadline.

The role of gamification in education was studied by Deterding et~al.\
\cite{deterding2011}, who found that elements such as points, badges, and
leaderboards can increase student motivation and engagement when thoughtfully
integrated. UniPlanner incorporates an experience point (XP) system with badges
and streaks, drawing on these findings to encourage consistent academic
participation.

From a technical perspective, the RESTful architectural style defined by
Fielding~\cite{fielding2000} provides the backbone for UniPlanner's client--server
communication, enabling a clean separation between the frontend interface and
backend data management. JSON Web Token (JWT)-based authentication, standardised
in RFC~7519~\cite{jones2015}, ensures stateless, secure session management across
all API endpoints.

The existing literature reveals a notable gap: most open-source LMS platforms
either lack built-in feedback mechanisms or require complex infrastructure to
deploy. UniPlanner addresses this gap by integrating a lightweight automated
feedback module directly into the application server, making structured feedback
available without reliance on external service dependencies.

\section{System Analysis}

UniPlanner was developed using the Agile Scrum methodology, which involves a
series of iterative development cycles called sprints. Initially, the requirement
analysis phase was conducted to gather and prioritise both functional and
non-functional requirements from all three user roles: student, teacher, and
administrator. Based on these requirements, the team created a product backlog
that guided each sprint. The system was designed incrementally, with the
architecture and UI evolving as new features were developed and validated.

\subsection{Requirement Analysis}

Before commencing development of UniPlanner, extensive requirement gathering was
carried out through analysis of existing LMS platforms, stakeholder interviews,
and review of academic workflows at Phoenix College of Management. Both functional
and non-functional requirements were identified.

\subsubsection{Functional Requirements}

The UniPlanner platform includes the following key functional requirements.

\begin{enumerate}[leftmargin=2.5em]
  \item \textbf{User Authentication and Authorisation:}
    The system must support secure login and registration for students, teachers,
    and administrators. Role-based access control must restrict API endpoints and
    UI features to authorised users only, enforced via JWT tokens with an 8-hour
    expiry.

  \item \textbf{Class and Course Management:}
    Teachers and administrators must be able to create, update, archive, and
    delete classes. Students must be able to enrol in classes using a class codeand track their progress per course.

  \item \textbf{Assignment Management:}
    Teachers must be able to create assignments with title, description, due date,
    maximum points, kind (assignment, quiz, project), and rubric criteria.
    Students must be able to view, submit, and track the status of their
    assignments.

  \item \textbf{Grading and Feedback:}
    Teachers must be able to grade student submissions via a SpeedGrader
    interface, providing scores and written feedback. The system must also provide
    automated pre-submission or manual feedback to students.

  \item \textbf{Resource Management:}
    Teachers and administrators must be able to upload, organise, and share
    learning resources (files, links) associated with specific classes.

  \item \textbf{Discussion Threads:}
    The system must support class-specific discussion boards where students and
    teachers can post and reply to messages.

  \item \textbf{Notifications:}
    The system must deliver real-time notifications for key events including new
    assignments, grading completions, class updates, and system announcements.

  \item \textbf{Calendar and Events:}
    The system must display upcoming deadlines, exam dates, and class sessions in
    a unified calendar view accessible to all roles.

  \item \textbf{Analytics Dashboard:}
    Each role must receive a customised analytics view: students see grades and
    streaks; teachers see class engagement and pending submissions; administrators
    see platform-wide usage metrics.

  \item \textbf{Admin Panel:}
    Administrators must be able to manage all users (create, update, delete), view
    platform activity, manage permissions, and reset the platform to a demo state
    for testing.

  \item \textbf{Automated Assistance Module:}
    The system must provide automated text summarisation, quiz generation from
    learning materials, assignment feedback, and discussion summarisation.

  \item \textbf{File Upload:}
    Users must be able to upload files as part of assignment submissions and
    resource management, with storage handled via Cloudinary cloud service.
\end{enumerate}

\subsubsection{Non-Functional Requirements}

Various non-functional requirements have been analyzed and identified, which are
outlined as follows:

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{Performance:} API responses must be returned within 200\,ms for
    standard CRUD operations. The frontend must remain interactive under
    concurrent user load.

  \item \textbf{Usability:} The UI must be intuitive and role-specific,
    minimising the number of clicks required to complete common tasks such as
    submitting an assignment or grading a submission.

  \item \textbf{Reliability:} The system must persist data to disk on every state
    mutation, ensuring no data loss in the event of a server restart.

  \item \textbf{Security:} All authenticated endpoints must validate JWT tokens.
    Passwords must be stored as SHA-256 hashes. CORS must be restricted to known
    origins in production.

  \item \textbf{Scalability:} The architecture must support replacement of the
    file-based store with a production database (PostgreSQL, MongoDB) without
    changes to the API contract.

  \item \textbf{Responsiveness:} The UI must render correctly on desktop
    (1280\,px+), tablet (768\,px), and mobile (375\,px) screen sizes using
    Tailwind CSS breakpoints.

  \item \textbf{Accessibility:} The platform must use semantic HTML and ARIA
    attributes to support screen reader compatibility.
\end{itemize}

\subsection{Feasibility Analysis}

To ensure the successful development and deployment of UniPlanner, a thorough
feasibility study was conducted evaluating the project from technical, operational,
economic, and scheduling perspectives.

\subsubsection{Technical Feasibility Study}

UniPlanner leverages widely adopted and well-documented technologies. Node.js with
Express.js provides a proven, lightweight backend framework capable of handling
RESTful APIs and file serving. Firebase offers reliable cloud-based data
synchronisation and authentication services. The frontend is built with vanilla
JavaScript modules and Tailwind CSS, eliminating complex build pipelines and
ensuring fast initial load times. All tools are open-source and freely available,
making the project technically feasible within the team's existing skill set.

\subsubsection{Operational Feasibility Study}

UniPlanner is designed with a strong emphasis on usability and role-specific
workflows. Each user role receives a tailored interface that surfaces only the
information and actions relevant to their responsibilities. The system requires
only a modern web browser, making it operationally feasible for users with varying
levels of technical expertise. Teachers can manage classes and assignments with
minimal training, and students can access their coursework from any device.

\subsubsection{Economic Feasibility Study}

The economic feasibility of UniPlanner is strong. All development tools---Node.js,
Express.js, Firebase (free tier), Tailwind CSS, and Cloudinary (free tier)---are
available at no cost. Deployment can be achieved on low-cost cloud platforms such
as Railway, Render, or a standard VPS for under \$10 per month. No additional
hardware is required by end users, as the platform runs entirely in a web browser.

\subsubsection{Schedule Feasibility Study}

System design is a crucial phase in the software development process that involves
defining the architecture, components, modules, and data flow of the system. It
transforms the requirements gathered during the analysis phase into a blueprint for
constructing the system. The design phase ensures that the system will be both
effective and efficient in meeting its functional and non-functional requirements.

how the data will flow throughout the system.

\section{Refinement of Classes and Object}

Initially, the identification and further refining of the essential classes will be
considered in the object-oriented system design. These classes mainly represent
entities of UniPlanner -- A Learning Management System. They are designed from the
functional requirements of the system. The following classes form the backbone of
the UniPlanner data model:

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{User:} Represents all platform users. Attributes:
    \texttt{id}, \texttt{name}, \texttt{email}, \texttt{role}
    (student/teacher/admin), \texttt{title}, \texttt{avatar}, \texttt{bio},
    \texttt{locale}, \texttt{xp}, \texttt{badges}, \texttt{passwordHash}.

  \item \textbf{Class:} Represents a course section. Attributes:
    \texttt{id}, \texttt{code}, \texttt{title}, \texttt{subject},
    \texttt{section}, \texttt{teacherId}, \texttt{teacherName},
    \texttt{color}, \texttt{description}, \texttt{progress},
    \texttt{archived}, \texttt{enrolledStudentIds}.

  \item \textbf{Assignment:} Represents a graded task. Attributes:
    \texttt{id}, \texttt{classId}, \texttt{title}, \texttt{kind},
    \texttt{dueDate}, \texttt{status}, \texttt{maxPoints},
    \texttt{submissions}, \texttt{averageScore}, \texttt{manualReview},
    \texttt{description}, \texttt{rubric}.

  \item \textbf{Submission:} Represents a student's response to an assignment.
    Attributes: \texttt{id}, \texttt{assignmentId}, \texttt{studentId},
    \texttt{contentText}, \texttt{fileName}, \texttt{fileUrl},
    \texttt{submittedAt}, \texttt{score}, \texttt{teacherFeedback},
    \texttt{plagiarismScore}, \texttt{qualityScore}, \texttt{lateFlag}.

  \item \textbf{Resource:} Represents shared learning materials. Attributes:
    \texttt{id}, \texttt{classId}, \texttt{title}, \texttt{type},
    \texttt{url}, \texttt{uploadedBy}, \texttt{createdAt}.

  \item \textbf{Discussion:} Represents a class discussion thread. Attributes:
    \texttt{id}, \texttt{classId}, \texttt{title}, \texttt{authorId},
    \texttt{posts} (array of Post objects).

  \item \textbf{Message:} Represents a direct message. Attributes:
    \texttt{id}, \texttt{fromId}, \texttt{toId}, \texttt{content},
    \texttt{sentAt}, \texttt{read}.

  \item \textbf{Notification:} Represents a platform notification. Attributes:
    \texttt{id}, \texttt{userId}, \texttt{title}, \texttt{description},
    \texttt{type}, \texttt{unread}, \texttt{createdAt}.

  \item \textbf{Event:} Represents a calendar item. Attributes:
    \texttt{id}, \texttt{title}, \texttt{type}, \texttt{date},
    \texttt{startTime}, \texttt{endTime}, \texttt{classId}.

  \item \textbf{AnalyticsEvent:} Records platform activity for analytics.
    Attributes: \texttt{id}, \texttt{userId}, \texttt{classId},
    \texttt{type}, \texttt{name}, \texttt{payload}, \texttt{createdAt}.
\end{itemize}

\section{Component Diagram}

The Component Diagram illustrates the relationship between the various components
of the system and how they interact with one another. It shows the high-level view
of the system's architecture from an object-oriented perspective.

\noindent\textbf{i.\ Frontend Component (Public Browser Client):}

Built with HTML5, Tailwind CSS, and vanilla JavaScript ES modules, the frontend
provides role-specific interfaces for all three user types. Key pages include:
Login, Dashboard (Student/Teacher/Admin), Classes, Assignments, Grading, Calendar,
Resources, Discussions, Messages, Analytics, Settings, and Admin Panel. The
frontend communicates with the backend exclusively via RESTful API calls using
the Fetch API.

\noindent\textbf{ii.\ Backend API Server (Node.js/Express.js):}

The Express.js server handles all API requests, enforces authentication via JWT
middleware, and delegates business logic to feature modules. Key modules registered
on the server include: Auth Module, Classes Module, Assignments Module, Submissions
Module, Resources Module, Discussions Module, Messages Module, Notifications
Module, Events Module, Analytics Module, and Upload Module (Cloudinary integration).

\noindent\textbf{iii.\ Data Store (LearningStore):}

UniPlanner uses a file-based JSON data store
(\texttt{server/data/learning-os.json}) managed by the \texttt{LearningStore}
class. The store maintains the full application snapshot including users, classes,
assignments, submissions, sessions, goals, permissions, and analytics events. Each
mutation is persisted to disk immediately, ensuring data durability across server
restarts.

\noindent\textbf{iv.\ Security Component:}

Authentication is implemented using a custom JWT library
(\texttt{server/security.js}) built on Node.js's built-in \texttt{crypto} module.
Tokens use HMAC-SHA256 signing with a configurable secret key and an 8-hour expiry.
Passwords are stored as SHA-256 hashes.

\noindent\textbf{v.\ Automated Feedback Module:}

The Automated Assistance Module (\texttt{server/ai.js}) provides four capabilities:
text summarisation, quiz generation, assignment feedback, and discussion
summarisation.

\noindent\textbf{vi.\ Cloud Storage (Cloudinary):}

File uploads are handled via the Cloudinary SDK. The frontend retrieves the
Cloudinary configuration from the backend API and uploads files directly to
Cloudinary's CDN. File metadata (URLs, names) is stored in the application data
store.

\section{Deployment Diagram}

The Deployment Diagram describes the physical deployment of the system's components
on hardware resources. It shows how the system's software is distributed across
various hardware nodes and how these nodes communicate with each other.

\noindent\textbf{i.\ Client Devices:}

Users access UniPlanner via any modern web browser on desktop, tablet, or mobile
devices. The frontend JavaScript modules and Tailwind CSS are served as static
assets from the Node.js server's \texttt{public/} directory. No installation is
required on the client side.

\noindent\textbf{ii.\ Application Server:}

The Node.js/Express.js server runs on a single cloud VM or container instance
(e.g., Railway, Render, or DigitalOcean). It serves both the static frontend assets
and the RESTful API endpoints under the \texttt{/api/v1/} prefix.

\noindent\textbf{iii.\ Firebase (Optional Real-time Sync):}

The architecture is designed to be Firebase-compatible, with the frontend store able
to subscribe to real-time updates. In production deployments, Firebase can replace
the file-based store for real-time multi-client synchronisation.

\noindent\textbf{iv.\ Cloudinary CDN:}

File uploads (assignment submissions, resource files) are stored in Cloudinary's
cloud CDN. Files are served directly from Cloudinary's edge network, reducing load
on the application server and providing fast global file delivery.

\noindent\textbf{v.\ Development Environment:}

During development, the frontend is served via Live Server (VS Code extension) on
port 5500, and the backend runs on a configurable port (default 3000). CORS is
configured to allow cross-origin requests from the Live Server origin.

\section{Implementation}

The implementation of UniPlanner was carried out in an iterative manner, following
the Agile Scrum approach. Each sprint delivered working functionality across both
the frontend and backend layers. This section outlines the tools, technologies,
and module-level implementation details.

\subsection{Tools Used}

The following tools were used for the development and implementation of UniPlanner:

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{Node.js (v20+):} Server-side JavaScript runtime used to build
    the Express.js API server.
  \item \textbf{Express.js (v4.x):} Lightweight web framework for defining
    RESTful API routes, middleware, and static file serving.
  \item \textbf{Firebase:} Cloud backend providing real-time database
    synchronisation and optional authentication services.
  \item \textbf{Cloudinary:} Cloud-based media storage and CDN used for handling
    file uploads from students and teachers.
  \item \textbf{Tailwind CSS (CDN):} Utility-first CSS framework used to build
    the responsive frontend UI without a build step.
  \item \textbf{Vanilla JavaScript (ES Modules):} Frontend scripting using
    native browser ES module imports, avoiding framework overhead.
  \item \textbf{JWT (custom implementation):} HMAC-SHA256 JSON Web Tokens for
    stateless authentication, implemented using Node.js's built-in
    \texttt{crypto} module.
  \item \textbf{VS Code + Live Server:} Primary development environment with
    live-reload for frontend development.
  \item \textbf{GitHub:} Version control and collaboration platform for source
    code management.
  \item \textbf{Figma:} UI/UX design tool used to create mockups and wireframes
    before implementation.
  \item \textbf{Postman:} API testing tool used to validate backend endpoints
    during development.
\end{itemize}

\subsection{Implementation Details of Modules}

UniPlanner is structured as a collection of independently registered Express.js
modules, each responsible for a specific domain of functionality:

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{Auth Module (\texttt{auth.module.js}):}
    Handles user login (\texttt{POST /api/v1/auth/login}) and session retrieval
    (\texttt{GET /api/v1/auth/me}). On successful login, a JWT token is issued
    and stored server-side.

  \item \textbf{Classes Module (\texttt{classes.module.js}):}
    Supports CRUD operations for course classes. Teachers can create classes
    with a unique enrolment code; students enrol using this code.

  \item \textbf{Assignments Module (\texttt{assignments.module.js}):}
    Teachers create assignments specifying class, title, kind, due date, max
    points, description, and rubric. Each assignment creation event is logged
    as an analytics event.

  \item \textbf{Submissions Module (via grading routes):}
    Students submit text content or file URLs against assignments. Teachers
    grade submissions via the SpeedGrader, providing a numeric score and written
    feedback.

  \item \textbf{Resources Module (\texttt{resources.module.js}):}
    Manages learning materials associated with classes. Teachers and admins can
    create resources; all enrolled users can view them.

  \item \textbf{Discussions Module (\texttt{discussions.module.js}):}
    Supports class-specific discussion threads. The automated module can generate
    a summary of discussion content on demand.

  \item \textbf{Messages Module (\texttt{messages.module.js}):}
    Enables direct messaging between users. Messages are stored with sender ID,
    recipient ID, content, and a read status flag.

  \item \textbf{Notifications Module (\texttt{notifications.module.js}):}
    Delivers system notifications to users. Notifications are marked as unread
    and displayed prominently on each role's dashboard.

  \item \textbf{Events Module (\texttt{events.module.js}):}
    Manages calendar events including deadlines, exams, and class sessions.

  \item \textbf{Automated Feedback Module (\texttt{ai.module.js} + \texttt{ai.js}):}
    Exposes automated capabilities via API routes for summarisation, quiz
    generation, pre-submission feedback, and thread summarisation.

  \item \textbf{Admin Module (\texttt{admin.module.js}):}
    Provides administrative functions including user management and a demo state
    reset endpoint. All admin routes require the \texttt{admin} role.

  \item \textbf{Upload Module (\texttt{upload.module.js}):}
    Manages file upload metadata after files are uploaded directly to Cloudinary
    from the browser.
\end{itemize}

\section{Result Analysis}

The testing phase revealed that UniPlanner functions as expected across all
modules. Unit tests passed successfully for individual components such as
authentication, assignment management, and grading. System tests confirmed that
the app's modules interact seamlessly, with notifications triggered accurately and
user data persisting correctly across server restarts.

Overall, the platform performed well during testing and is ready for deployment
after minor optimizations based on user feedback.

\chapter{Conclusion and Future Recommendations}

\section{Conclusion}

UniPlanner -- A Learning Management System successfully delivers a unified,
role-aware educational platform that addresses the fragmentation of traditional
academic management tools. Through its student, teacher, and administrator
portals, the platform consolidates course management, assignment tracking,
grading, resource sharing, communication, and analytics into a single web
application.

The implementation demonstrates that a lightweight Node.js/Express.js
architecture, combined with a responsive Tailwind CSS frontend and Firebase-backed
data persistence, can deliver a production-grade LMS without the complexity and
cost of enterprise platforms. The built-in automated feedback module provides
practical educational value through pre-submission feedback, quiz generation, and
discussion summarisation---features that directly support formative assessment
best practices identified in the literature.

The security architecture, built on custom JWT authentication with HMAC-SHA256
signing and role-based access control enforced at every API endpoint, ensures
that the system is secure against common authentication vulnerabilities. All unit
and system test cases passed, confirming the platform's correctness and
reliability.

In conclusion, UniPlanner fulfils all defined project objectives and provides a
solid foundation for a production-ready LMS that can serve the academic needs of
institutions like Phoenix College of Management. The project also demonstrates the
practical applicability of modern web development skills acquired during the BIT
programme.

\section{Future Recommendations}

To improve the platform and address current limitations, future work could
focus on:

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{Real-time Collaboration via WebSockets:}
    Replace or supplement the current polling-based state updates with WebSocket
    connections (Socket.IO) to enable true real-time collaboration in discussion
    threads, notifications, and live assignment status updates.

  \item \textbf{Native Mobile Application:}
    Develop native iOS and Android applications using React Native or Flutter to
    provide push notification support, offline access, and a mobile-optimised
    experience for students who primarily use smartphones.

  \item \textbf{PostgreSQL or MongoDB Backend:}
    Migrate from the file-based JSON store to a production-grade relational
    (PostgreSQL) or document (MongoDB) database to support multi-instance
    deployment, concurrent writes, and complex analytical queries.

  \item \textbf{Video Conferencing Integration:}
    Integrate with Zoom, Google Meet, or Jitsi Meet APIs to enable teachers to
    schedule and launch virtual class sessions directly from the UniPlanner
    calendar.

  \item \textbf{Plagiarism Detection:}
    Integrate a plagiarism detection engine (e.g., Turnitin API or open-source
    alternatives) to automatically flag potentially plagiarised submissions
    during the grading workflow.

  \item \textbf{Multi-language Support:}
    Add internationalisation (i18n) support to enable the platform to serve
    non-English speaking institutions, starting with Nepali language support for
    the local context.
\end{itemize}

\section{Data Schema}

The UniPlanner data schema is defined as a flat JSON document persisted in
\texttt{server/data/learning-os.json}. The top-level snapshot object contains
the following collections:

\begin{itemize}[leftmargin=2.5em]
  \item \textbf{\texttt{app.users[]}:} Array of User objects containing
    \texttt{id}, \texttt{name}, \texttt{email}, \texttt{role}, \texttt{title},
    \texttt{avatar}, \texttt{bio}, \texttt{locale}, \texttt{xp},
    \texttt{badges}, \texttt{passwordHash}.

  \item \textbf{\texttt{app.classes[]}:} Array of Class objects containing
    \texttt{id}, \texttt{code}, \texttt{title}, \texttt{subject},
    \texttt{section}, \texttt{teacherId}, \texttt{teacherName},
    \texttt{color}, \texttt{description}, \texttt{progress}, \texttt{archived},
    \texttt{enrolledStudentIds}.

  \item \textbf{\texttt{app.assignments[]}:} Array of Assignment objects
    containing \texttt{id}, \texttt{classId}, \texttt{title}, \texttt{kind},
    \texttt{dueDate}, \texttt{status}, \texttt{maxPoints}, \texttt{submissions},
    \texttt{averageScore}, \texttt{manualReview}, \texttt{description},
    \texttt{rubric}.

  \item \textbf{\texttt{app.resources[]}:} Array of Resource objects containing
    \texttt{id}, \texttt{classId}, \texttt{title}, \texttt{type}, \texttt{url},
    \texttt{uploadedBy}, \texttt{createdAt}.

  \item \textbf{\texttt{app.discussions[]}:} Array of Discussion objects
    containing \texttt{id}, \texttt{classId}, \texttt{title}, \texttt{authorId},
    and a \texttt{posts} array.

  \item \textbf{\texttt{app.messages[]}:} Array of Message objects containing
    \texttt{id}, \texttt{fromId}, \texttt{toId}, \texttt{content},
    \texttt{sentAt}, \texttt{read}.

  \item \textbf{\texttt{app.notifications[]}:} Array of Notification objects
    containing \texttt{id}, \texttt{userId}, \texttt{title},
    \texttt{description}, \texttt{type}, \texttt{unread}, \texttt{createdAt}.

  \item \textbf{\texttt{app.events[]}:} Array of Event objects containing
    \texttt{id}, \texttt{title}, \texttt{type}, \texttt{date},
    \texttt{startTime}, \texttt{endTime}, \texttt{classId}.

  \item \textbf{\texttt{submissions[]}:} Array of Submission objects containing
    \texttt{id}, \texttt{assignmentId}, \texttt{studentId},
    \texttt{contentText}, \texttt{fileName}, \texttt{fileUrl},
    \texttt{submittedAt}, \texttt{score}, \texttt{teacherFeedback},
    \texttt{submissionFeedback}, \texttt{plagiarismScore},
    \texttt{qualityScore}, \texttt{lateFlag}.

  \item \textbf{\texttt{analyticsEvents[]}:} Array of AnalyticsEvent objects
    containing \texttt{id}, \texttt{userId}, \texttt{classId}, \texttt{type},
    \texttt{name}, \texttt{payload}, \texttt{createdAt}.

  \item \textbf{\texttt{sessions[]}:} Array of active Session records containing
    \texttt{token}, \texttt{userId}, \texttt{role}, \texttt{issuedAt},
    \texttt{expiresAt}.

  \item \textbf{\texttt{goals[]}:} Array of Goal objects containing \texttt{id},
    \texttt{userId}, \texttt{title}, \texttt{targetType}, \texttt{targetValue},
    \texttt{progressValue}, \texttt{dueAt}, \texttt{status}.

  \item \textbf{\texttt{permissions[]}:} Array of Permission objects containing
    \texttt{id}, \texttt{userId}, \texttt{permissionKey}, \texttt{scopeType},
    \texttt{scopeId}, \texttt{createdAt}.
\end{itemize}
